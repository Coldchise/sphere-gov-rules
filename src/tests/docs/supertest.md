# Supertest — backend HTTP endpoint integration tests

**Belongs to:** backend. **Folder:** `src/tests/integration/backend/`. **Test runner:** Vitest in `node`. Supertest issues HTTP requests to an app/server and asserts response status, headers and body; it is not a replacement for a runner or real DB.

## Use it when

- Testing `/api/users`, `/api/auth/login`, employee lists, pagination, sorting, search, multipart upload.
- Confirming HTTP contract: 200/201, 400/422 validation, 401 anonymous, 403 forbidden, 404, 409 duplicates, 429 rate limit when configured.
- Verifying cookie security attributes, request limits, safe error response and persistence.
- Testing authorization using multiple **test-only identities**.

## Setup

```bash
npm install -D vitest supertest @types/supertest
# Install express only if it is your chosen backend framework.
```

Expose an actual app factory without immediately binding to a fixed port so Supertest can test it:

```ts
// backend/src/app.ts -- illustrative Express architecture
import express from 'express';
export function createApp() {
  const app = express();
  app.use(express.json({ limit: '100kb' }));
  // app.use('/api', actualRouters);
  return app;
}
// backend/src/server.ts separately calls createApp().listen(port)
```

Use your existing router framework/app factory. Do not create a parallel fake app that bypasses auth middleware; keep production middleware active.

## Example test with real route (adapt actual API)

```ts
// src/tests/integration/backend/users.test.ts
import { describe, expect, it } from 'vitest';
import request from 'supertest';
import { createApp } from '../../../app';

const app = createApp();

describe('GET /api/users', () => {
  it('requires login', async () => {
    const res = await request(app).get('/api/users');
    expect(res.status).toBe(401);
    expect(res.body).not.toHaveProperty('passwordHash');
  });

  it('rejects invalid pagination instead of querying with unbounded size', async () => {
    const res = await request(app)
      .get('/api/users?page=1&limit=1000000')
      .set('Authorization', `Bearer ${process.env.TEST_USER_TOKEN ?? ''}`);
    // Choose an exact code and max page size AFTER checking your real API contract.
    expect([400, 422]).toContain(res.status);
  });
});
```

**Important:** Example token is not generated by the starter. Proper integration tests should programmatically seed/create a test user and obtain a scoped test token or use a test-only auth adapter; do not hardcode a valid token or use production credentials. Prefer exact expected status once the API contract is known, not broad accepted-status arrays.

## Test matrix

| Route | Case | Expected |
|---|---|---|
| `POST /api/users` | valid authorized payload | 201, correct fields, row persisted |
| `POST /api/users` | missing field | agreed 400/422 response, no new row |
| `POST /api/users` | duplicate email | 409 (if contract uses 409), no duplicate |
| `GET /api/users` | no auth | 401; no records |
| `GET /api/users` | wrong role | 403; no records |
| `GET /api/users` | cross-tenant access | 403/404; no data disclosure |
| `GET /api/users?limit=999999` | excessive page size | bounded server cost or 400/422 |
| `PATCH /api/users/:id` | forbidden field (e.g. role) | rejected/ignored; DB unchanged |
| file upload | forbidden MIME/oversize | 400/413/415 as contract states |

**Do not** trust a UI-disabled button for permissions; send the HTTP request directly and assert server-side denial.

## Test with DB (recommended for persistence)

Combine with Testcontainers when verifying real inserts, unique constraints, database transactions and data isolation. Supertest may use an in-memory dependency for **pure route-layer contract** tests, but do not claim that covers SQL behavior. `request.agent(app)` can preserve cookies for session flows; use separate agents for different users.

## Security requirements

- Exercise expired/malformed token, unauthenticated 401, forbidden 403, path ID mismatch, allowed-method enforcement.
- Check cookies are `HttpOnly`, `Secure` for HTTPS, and appropriate `SameSite` for your deployment; cookie-session flows may need CSRF testing.
- Validate response does not include secret keys, password hash, stack trace, raw SQL, or sensitive user record.
- Check body-size/rate limits if configured; do not generate heavy traffic or stress production.
- Never print auth headers or test tokens on failure.
